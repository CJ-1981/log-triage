# Tech — Log Triage

Product type: Web Browser App (single self-contained HTML file)

## TECHNOLOGY STACK SPECIFICATIONS

- Application language: vanilla JavaScript (UMD modules), no framework, no runtime dependencies.
- Styling: hand-written CSS with theme variables generated from `src/themes.js` at build time (six themes via `body[data-theme]`).
- Build and test toolchain: Node.js 22 (build and tests only — the built HTML has no Node dependency).
- Test runner: the Node built-in `node:test` runner.
- End-to-end testing: Playwright (`^1.48.0`), the only devDependency.
- License / packaging: MIT, private npm package.

## FRAMEWORK DECISIONS

Why vanilla JS UMD modules instead of a framework or bundler:

- Zero dependencies: the deliverable is one self-contained HTML file; any framework would either pull CDN/runtime code (breaking the no-network invariant) or require a real bundler and transpile step.
- Single-file output: `build.js` is a token-substitution concatenator, not a bundler. Modules are UMD so the identical file runs in Node (tests, coverage gate), in the browser, and inside the inlined worker bundle.
- Longevity and auditability: a privacy tool should be readable as shipped. The generated `log-triage.html` contains the concatenated sources verbatim, with no minified or transformed intermediate layer.
- Worker compatibility: the paging worker is spawned from a Blob URL built from an inlined pure-logic module subset; this requires modules that are order-concatenatable and free of import machinery.

External-format support is likewise dependency-free by design: gzip uses the browser-native `DecompressionStream`; tar, zip, and 7z containers are parsed and written by project modules (`src/archive.js`, `src/format-7z.js`); LZMA1/LZMA2 decoding is a pure-JS implementation (`src/lzma.js`, ADR-0011) — no WASM, no CDN code.

## DEVELOPMENT ENVIRONMENT

Requirements: Node.js 22. npm scripts (`package.json`):

- `npm test` — unit suites across thirteen test files (`node --test`).
- `npm run test:gate` — unit tests plus the coverage gate via `tools/coverage-gate.mjs` (90% line / 85% branch minimum on core src modules).
- `npm run build` — build `log-triage.html` from `src/` (`node build.js`).
- `npm run e2e` — Playwright end-to-end tests (99 app specs + 8 stress specs).
- `npm run e2e:stress` — stress suite only, over a big fixture generated by `tools/genbig.mjs`.
- `npm run bump` — conventional-commit semver bump (`tools/bump.mjs`; CI runs this automatically on `main`).

Local browser testing uses `tools/serve.mjs` (tiny static server); screenshots for the README are captured with `tools/shots.mjs`.

## BUILD PIPELINE

- `node build.js` concatenates `src/` UMD modules (26 modules in `MODULE_ORDER`), the stylesheet, the worker bundle (7 modules in `WORKER_ORDER`, inlined as a string for a Blob-URL Worker), the shared test case suite, and an inline demo log into `template.html`, producing the single self-contained `log-triage.html`.
- All inputs are LF-normalized so a Windows CRLF checkout yields a byte-identical bundle to CI; token replacement uses function replacers so `$`-sequences in module sources are never expanded.
- Version stamping: `__LT_VERSION__` is kept in sync across `package.json`, the README marker (`<!-- version: … -->`), and `docs/changelog.md` by `tools/bump.mjs`.
- CI verifies the committed bundle is fresh: after building, `git diff --exit-code -- log-triage.html` fails the run if the committed HTML does not match the sources.

## TESTING STRATEGY AND TOOLS

- Shared-case strategy: `tests/core-cases.js` defines named input → expected cases over the core modules and powers both `node --test` and the in-browser `?selftest` page, so the exact same suite runs in Node and the browser.
- Unit coverage: detection, parsing, masking, filters, highlights, levels, search, paging, droptree, store, export, export streaming, export archives, 7z container, PII remote adapters, bump tooling.
- Coverage gates: `tools/coverage-gate.mjs` enforces 90% line / 85% branch minimum per core module and fails loudly if a gated module produces no coverage row; only the three browser-only glue modules (`app.js`, `app-filecache.js`, `app-paging.js`) are exempt.
- E2E: Playwright (Chromium in CI) with 99 app specs and 8 stress specs over a generated multi-GB-scale fixture with deterministic RAREJUMPMARKER lines every 100k lines.
- Fixtures: committed logs (`demo.log`, `syslog.log`, `apache.log`, `service.log`, `suspend.log`, dlt-viewer sample) plus LZMA hex fixtures; 7z/zip container tests build real archives with the local 7-Zip CLI when available and skip cleanly without it.
- Development process: TDD with quality gates G0–G8 (scaffold, parsing, masking, filters, search, store/timeline/selection/bookmarks, export/bump tooling, themes/UI, e2e hardening), each with entry/exit criteria in `docs/test-plan.md` — all complete since v1.0.0; new features follow the same gate discipline.

## CI/CD AND DEPLOYMENT

GitHub Actions workflow (`.github/workflows/ci.yml`), Node 22 on ubuntu-latest:

- On every push to `main` and every pull request: install, install `p7zip-full`, run `npm run test:gate`, build, verify the committed bundle is fresh, install the Playwright Chromium browser, run `npm run e2e`, upload the built HTML as an artifact.
- On push to `main` only, a release job then: runs `node tools/bump.mjs --ci` (conventional commits drive the semver level — feat minor, fix patch, `!`/BREAKING CHANGE major), rebuilds the bundle with the release version, pushes the release commit and `vX.Y.Z` tag as a release bot, assembles the site (`log-triage.html` copied to `site/index.html`), and deploys to GitHub Pages via the official Pages actions.
- Pages deployment lives inside the release job deliberately: the release commit is pushed with `GITHUB_TOKEN`, which does not trigger further workflow runs, so a standalone Pages job would serve a stale bundle forever.
- Live deployment target: https://cj-1981.github.io/log-triage/ (current release v1.53.2).

## BROWSER SUPPORT MATRIX

- Any modern Chromium-based browser and Firefox: fully supported.
- Safari 16.4 and later: supported (required for lookbehind regexes).
- Runs offline from `file://` with no installation; Node.js is never needed at runtime.
- Mobile: supported with a responsive layout — the files panel becomes an overlay drawer, the mask grid stacks, and the viewer toolbar collapses behind an overflow button at phone width.

## NO-NETWORK / PRIVACY INVARIANT

The no-network constraint is an architectural invariant, not a policy:

- No CDN assets, no external fonts, no analytics, no telemetry of any kind; all archive decoding and PII analysis default to in-page implementations.
- The default PII provider is the local regex engine and makes zero network calls; remote providers (Presidio sidecar, LLM API) are opt-in, off by default, warn that data would leave the machine, and store API keys only locally, never in exported config files (FR-25, ADR-0003, ADR-0010).
- Remote-provider HTTP is injected (`fetchImpl`) in `src/pii-remote.js`, keeping the core testable without a network and keeping the offline path free of fetch calls.
- Masking is lazy: raw lines are stored locally and masking applies at render/copy/export time; the exporter contract forbids unmasking.
- Any proposed dependency must satisfy: pure JS (no WASM), no network fetch, inlinable as UMD source in the single-file build.

## PERFORMANCE CHARACTERISTICS

- Multi-GB files are handled by full-file columnar indexing in a dedicated worker: Float64 byte offsets (exact for large offsets), packed timestamp keys, level codes; pages (500 rows in the viewer, 256-row fetch units in the worker) are materialized on demand from `File.slice` behind a byte-bounded LRU cache.
- A configurable per-file analysis sample (default 100,000 lines, head + newest tail) bounds only the analysis tab; viewing, filtering, search, and paging always cover every indexed line.
- Deep-scan search re-streams files from disk with capped results (default 10,000); exports stream chunk-by-chunk to the sink without holding the whole output in memory, and archive exports stream to the saved file for zip/tar/tar.gz (any size) while 7z export stays bounded to a 32 MiB buffer.
- Debounced inputs (search 250 ms, quick filter 200 ms) keep typing responsive; a point-in-time performance review exists at `docs/performance-review-2026-09-15.md`.

## TECHNICAL CONSTRAINTS AND CONSIDERATIONS

- Single-file constraint bounds what can be added: every feature must be source-inlinable and dependency-free.
- The worker bundle must remain free of UI glue so it can run standalone from a Blob URL.
- Safari compatibility requires avoiding regex features newer than lookbehind support.
- Encrypted or filter-chained 7z archives fail with readable errors rather than partial extraction; entries over 512 MB are skipped with an announced message, with the documented exception of `dumpstate_board.bin` ramdumps, which are stream-converted to a capped 64 MB text entry.
- The 7z writer emits stored (copy) entries only — LZMA encoding is deliberately not implemented — so exported `.7z` files keep container structure without recompression.
- Conventional commits are mandatory: the release automation derives versions from commit messages.
