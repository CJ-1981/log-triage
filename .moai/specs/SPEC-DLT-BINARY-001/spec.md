## Assumptions

- ADR-0014's recorded design is the locked architecture for this SPEC; no re-derivation of the approach happens at implementation time. Confidence: High (evidence: ADR-0014 status "accepted (v1.43.0)" in `docs/decisions.md`).
- Binary .dlt captures may appear with or without the storage header; when absent, a plausible DLT v1 standard header at offset 0 (4-byte base plus optional extras, at most 16 bytes total) is the classification signal. Both shapes exist in the wild per the DLT specification and ADR-0014's framing description. Confidence: High.
- The new format id is `dlt-binary`, distinct from the existing text format id `dlt`; the two detection paths stay mutually exclusive because one is byte sniffing in `PagedLog.index` and the other is text scoring in `detect.js`. Confidence: High (evidence: detection flow at `src/paged.js:74-79`).
- FIBEX signal-dictionary support is OUT of scope for this SPEC; non-verbose payloads render as hex dumps. A dictionary, if ever added, is an optional refinement (R4-6). Confidence: High (evidence: ADR-0014 defers FIBEX).
- Storage-header timestamps (uint32 seconds since epoch plus int32 microseconds) convert to UTC-naive MM-DD HH:MM:SS.mmm, dropping the year, per ADR-0004; the standard-header TMSP field is a uint32 counter in 0.1 ms units relative to system start with no epoch base, so it is consumed for framing only and never normalized into the time column. Lexicographic order must equal chronological order within a capture. Confidence: High.
- 64- and 128-bit integer arguments require BigInt decoding because Float64 loses precision above 2^53; the decoder must not round-trip them through Number. Confidence: High.
- Page size stays 256 rows and the paging/worker contract (stateless worker, bounded caches) is unchanged; binary records are just new content behind the same offsets contract. Confidence: High (evidence: `src/paged.js:87-105`).
- The DLT log-level nibble maps onto the existing severity vocabulary used by chips and level colors (fatal F, error E, warn W, info I, debug D, verbose V), exactly as the `dlt` text parser already maps subtype strings today. Confidence: High (evidence: parse group in `tests/core-cases.js:185-222`).

## Requirements (EARS)

### M1 — Detection and classification

- R1-1 [Event-driven] WHEN a dropped file's first bytes at offset 0 equal the DLT storage-header magic 44 4C 54 01 (ASCII "DLT" followed by version byte 0x01), THEN the system shall classify the file as format `dlt-binary` in `PagedLog.index` and route it to the binary record-iterator indexing path instead of the `byteLines` text line splitter; any positive `dlt-binary` classification (by this requirement or R1-2) shall also set the strict UTF-8 head flag (`this.utf8`) to true, because that flag drives the text-quality encoding badge (`src/app.js:485`, `src/app.js:517`) and rendered binary text is produced by the decoder, not by TextDecoder replacement.
- R1-2 [Event-driven] WHEN a dropped file has no storage header at offset 0, THEN the system shall classify it as format `dlt-binary` only when ALL of the following hold, so storage-header-less captures index correctly while ordinary text files are never misrouted: the first bytes form a plausible DLT v1 standard header — an HTYP typed-flags byte whose protocol-version bits equal 0b001 and whose five flag bits UEH 0x01, MSBF 0x02, ECU 0x04, SESS 0x08, and TMSP 0x10 form a consistent combination, plus a total length read in the byte order given by the MSBF bit; the declared total length is at least the minimum header size implied by HTYP and fits within `file.size`; a chained look-ahead holds — the boundary at the offset plus the declared length must itself start a plausible header (at least two consecutive plausible boundaries), or the first message must decode to a complete typed structure; and a text veto applies — a head that `detector.detectFormat` scores at 0.5 confidence or higher for any text format is not classified `dlt-binary`. The single-header check alone is NOT sufficient: the protocol-version bits are bits 5-7, so every first byte in 0x20 through 0x3F passes them (digits and dashes included), letting a plain text head form a consistent single header with a large little-endian length. The chained look-ahead and the veto consume only the already-buffered head, so the sniff stays in `src/paged.js` per R1-4 and stays layered above the text scorer per R1-3.
- R1-3 [State-driven] WHILE the text auto-detect path in `PagedLog.index` assigns `this.format` from the first buffered `byteLines` rows via `detector.detectFormat`, the system shall keep the text `dlt` detection (built on `RE_DLT`) and the new `dlt-binary` byte sniff mutually exclusive, so a dlt-viewer text export continues to detect as `dlt` and never as `dlt-binary`, and a binary capture is never misclassified as a text format.
- R1-4 [Ubiquitous] The system shall implement the `dlt-binary` sniff as a bounded magic-byte and header-plausibility check over the already-buffered head bytes inside `src/paged.js`, following the `is7z` precedent in `src/format-7z.js`, and shall keep `src/detect.js` a pure text-line scorer with no binary magic checks.
- R1-5 [Event-driven] WHEN classification as `dlt-binary` completes, THEN the system shall record on the index whether the 16-byte storage header (4-byte magic 44 4C 54 01, 4-byte ECU id, uint32 seconds since epoch, int32 microseconds) is present, and the record iterator shall treat that header as framing rather than payload. Only storage-header version 0x01 is in scope per ADR-0014; the variable-length DLTv2 (version 0x02) storage header is a documented non-goal, pinned by the AC-1.6 negative classification case. The per-file presence flag is advisory framing metadata, not a per-record skip rule: a single capture may mix storage-header-prefixed and storage-header-less messages (AC-E.9), so the record iterator shall detect the 44 4C 54 01 magic at each record boundary and skip the 16 bytes only where that magic is actually present.

### M2 — Indexing and record iteration

- R2-1 [Event-driven] WHEN `PagedLog.index` processes a `dlt-binary` file, THEN the system shall walk message boundaries instead of splitting lines: the optional 16-byte storage header (R1-5); the standard header, whose 4-byte fixed part is the HTYP typed-flags byte (bits UEH 0x01, MSBF 0x02, ECU 0x04, SESS 0x08, TMSP 0x10), the mcnt message counter, and a 16-bit total length transmitted in the byte order given by the MSBF bit (big-endian in dlt-daemon captures, which always set MSBF), followed by the optional 4-byte ECU id when ECU is set, the optional 4-byte session id when SESS is set, and the optional uint32 timestamp when TMSP is set (a counter in 0.1 ms units relative to system start); and, when UEH is set, the fixed 10-byte extended header (the msin message-info byte with the VERB verbose flag at bit 0, the MSTP message type in bits 1-3, and the MTIN log level in bits 4-7 as the high nibble; a mandatory 1-byte argument count immediately after msin; the 4-byte application id APID; the 4-byte context id CTID).
- R2-2 [Ubiquitous] The system shall push each message's START byte offset into `this.offsets` (the existing `Column` over `Float64Array`) so that `PagedLog.page` can slice and re-decode exactly the messages of one page, preserving the blocked bounded-memory model.
- R2-3 [Event-driven] WHEN a message carries a storage-header timestamp (uint32 seconds since epoch plus int32 microseconds), THEN the system shall decode it and push the normalized numeric value via `timeKey` into `this.times` so `sortIds`, `metadata`, and every time-range feature keep working unchanged; the standard-header TMSP field, a relative 0.1 ms counter with no epoch base, is consumed for framing only and never pushed into `this.times`.
- R2-4 [State-driven] WHILE a message carries no storage-header timestamp, the system shall apply the existing carry-forward semantics of `add()` (`src/paged.js:66-68`): `this.times` receives the predecessor record's time key (never a null or zero key, which would sort before all timestamped records) and the null-timestamp state is recorded as bit 128 in `this.levels`, read back by `metadata()` (`src/paged.js:82-84`), exactly as text records do today, and the record attaches to the preceding parsed line's context under ADR-0004.
- R2-5 [Ubiquitous] The system shall keep binary indexing cooperative under the same yield contract as `byteLines` (the `pause()` helper with an 8 ms deadline per chunk), honoring the `cancelled` callback and reporting progress through the existing `onProgress` parameter of `index(onProgress, cancelled, sampleLimit)`.
- R2-6 [Event-driven] WHEN indexing of a `dlt-binary` file completes, THEN the system shall return the same head+tail analysis sample array shape that text indexing returns, built from decoded message lines limited by `sampleLimit`, so the paging app and `issues.js` consume one shape for all formats.
- R2-7 [Ubiquitous] The system shall implement the DLT binary decoder as a new pure UMD module registered in `build.js` WORKER_ORDER ahead of the `paged.js` entry, containing no UI glue, so the paging-worker bundle keeps running standalone from a Blob URL, respects UMD order-concatenation dependencies (`util.js` first, consumer after producer), and the `tests/scaffold.test.js` bundle assertion continues to pass.

### M3 — Page decoding and rendering

- R3-1 [Event-driven] WHEN `PagedLog.page` serves rows from a `dlt-binary` file, THEN the system shall read one `file.slice` spanning `this.offsets.get(first)` through the last offset of the 256-row page and re-decode only those records, replacing the CR/LF stripping of text pages with per-message binary decode.
- R3-2 [Ubiquitous] The system shall render each decoded message as exactly one text line and expose it through the existing record shape built by `PagedLog.record` (`fileId`, `file`, `lineNo`, `seq`, `raw`, plus parsed `ts`, `level`, `tag`, `pid`, `msg`), so `PagedLog.get`, `PagedLog.metadata`, filters, search, masking, quick scan, and export operate without format-specific branches. The worker raw-scan path is in scope: the `rawNeeded` loops in `src/app-paging-worker.js` (line 49 for query, line 110 for `exportInit` — full search, quick scan, any enabled non-highlight filter rule, and the export archive scan) iterate `LT.byteLines` directly today and index `metadata(i)` in BYTE-LINE index space, which is wrong for binary records; the system shall expose one format-agnostic record iterator on `PagedLog` (the `byteLines` splitter for text formats, the R2 record iterator for `dlt-binary`) and point both loops at it, so matches on a binary capture resolve to decoded records in the correct record index space. A unit test shall pin that a search or quick-scan hit on a binary capture resolves to the decoded record, not a raw byte-line.
- R3-3 [Event-driven] WHEN a message carries a storage-header timestamp, THEN the system shall normalize its DLT epoch seconds and microseconds to the year-less UTC-naive MM-DD HH:MM:SS.mmm model via the existing `timeText` round-trip so lexicographic order equals chronological order per ADR-0004; the standard-header TMSP relative counter is not a time-column source because it carries no epoch base.
- R3-4 [Event-driven] WHEN a message's MTIN log-level nibble (the high nibble, bits 4-7, of the msin byte) is decoded, THEN the system shall map it onto the existing severity vocabulary and level letters (fatal F, error E, warn W, info I, debug D, verbose V) exactly as `parser.parseLine` maps the `dlt` text format's subtype strings today, so level chips and colors are shared by both DLT ingest paths.
- R3-5 [Event-driven] WHEN a message's MSTP bits identify a non-log type, THEN the system shall render it with the same stable keyword prefixes the `dlt` text path uses — app_trace, nw_trace, and control for MSTP values 1 through 3, and extension for MSTP value 4 (EXTENSION), which the text path's `RE_DLT` (`src/detect.js:17`) already renders — and WHEN the MSTP value is a reserved value 5 through 7, THEN the system shall render a stable deterministic literal prefix (`mstp=N`) so every 3-bit MSTP value has exactly one pinned rendering, keeping issue patterns, chips, and drawer fields uniform across both paths and keeping the R5-6 determinism guarantee total.
- R3-6 [Event-driven] WHEN the analysis sample is collected during indexing with `sampleLimit` rows, THEN the system shall draw its sample lines from the decoded `dlt-binary` messages so `issues.js` patterns, masking, and quick scan see the same rendered text they would for the `dlt` text format; quick scan's worker scan runs over the same format-agnostic record iterator as the other raw-scan paths per R3-2, so its hits index into the decoded record space as well.

### M4 — Argument decoding

- R4-1 [Event-driven] WHEN a message is verbose (UEH set and the verbose flag set in the message info), THEN the system shall decode its payload as a sequence of typed arguments, each headed by a 32-bit type info word carrying the type code, TLEN length field, variable-length flag, and string-encoding bits, and shall render the arguments space-separated into one dlt-viewer-like text line.
- R4-2 [Ubiquitous] The system shall support the full DLT argument type set: boolean, signed and unsigned integers of 8, 16, 32, 64, and 128 bits, float16, float32, and float64, ASCII and UTF-8 strings, and raw payloads, decoding 64- and 128-bit integers exactly via BigInt so no value loses precision through Float64.
- R4-3 [Event-driven] WHEN a string argument's encoding bits select UTF-8, THEN the system shall decode it with a UTF-8 decoder and render each invalid byte as a lowercase two-digit `\xNN` hex escape — the pinned visible lossless placeholder, so the original bytes stay recoverable and filter and search behavior over the placeholder is deterministic; WHEN the bits select ASCII, THEN the system shall decode one byte per character.
- R4-4 [Unwanted] The system shall not skip or drop a message because its payload is non-verbose; IF a message is non-verbose and no FIBEX signal dictionary is loaded, THEN the system shall render its payload as a hex dump line with a stable prefix so every captured byte remains visible to filter, search, and export.
- R4-5 [State-driven] WHILE arguments are decoded, the system shall bound each argument read by the message's declared total length and the remaining payload, and shall treat a read past that boundary as an invalid argument handled per M5 rather than reading into the next message's bytes.
- R4-6 [Optional-feature-state] WHERE a FIBEX signal dictionary covering the message's APID and CTID is available, the system may render non-verbose payloads using dictionary signal interpretations instead of the hex dump; WHERE such a dictionary is absent, the system shall render the hex dump line per R4-4.

### M5 — Resilience and diagnostics

- R5-1 [Unwanted] The system shall not abort indexing of a `dlt-binary` file on the first malformed message; IF a message is truncated at end of file, THEN the system shall decode its leading valid portion as a partial record, count one warning, and finish the index. Precedence: this partial-record handling applies only when at least the message header itself is complete; a header-only tail with zero indexed records is a clean empty capture (AC-E.6), not a partial record and not a resync failure; and a lone standard header whose declared total length equals its own header size completes as framing and yields zero records — an empty message is not a record.
- R5-2 [Unwanted] IF a message's length framing is implausible (total length below the minimum header size implied by HTYP, or overshooting `file.size`), THEN the system shall resynchronize by scanning forward to the next plausible storage-header magic or plausible standard header, count the desynchronization as a warning, and continue indexing from the recovered boundary.
- R5-3 [Unwanted] IF an argument's type info or TLEN is invalid during verbose decode, THEN the system shall render the remaining payload of that message as a hex dump, count the warning, and leave all subsequent messages intact.
- R5-4 [Event-driven] WHEN resynchronization cannot find any plausible next boundary within the remaining bytes, THEN the system shall fail loudly with a descriptive error naming the byte offset and the number of records indexed so far, instead of silently producing a partial or empty index.
- R5-5 [Event-driven] WHEN a `dlt-binary` index completes with one or more resynchronization or decode warnings, THEN the system shall surface the warning count through the existing status and metadata surfaces so users can see that decoding was lossy.
- R5-6 [Ubiquitous] The system shall keep every `dlt-binary` decode and resynchronization decision deterministic, so identical bytes produce identical record offsets, rendered lines, and warning counts on every indexing and page re-decode.

## Constraints

Technical constraints:

- Pure JavaScript only; no WASM, no native dependencies, no network access at runtime.
- All `src/` modules stay UMD and order-concatenatable; the new decoder must respect bundle order (`util.js` first; the decoder before `paged.js` when `paged.js` consumes it).
- The paging-worker bundle (`build.js` WORKER_ORDER) must remain free of UI glue and runnable standalone from a Blob URL; the single-file HTML build invariant must not be broken.
- Safari-safe regular expressions only (lookbehind permitted); no regex features beyond the existing engine baseline.
- Coverage gate holds at 90 percent line / 85 percent branch for the new decoder module; a gated module with no coverage row is a hard gate failure in `tools/coverage-gate.mjs`.
- Existing behavior of the `dlt` text format (detection, parsing, chips, masking, and the e2e assertions around `tests/fixtures/dlt-viewer-sample.txt`) must not regress.
- The bounded-memory model is preserved: blocked `Column` storage, 256-row pages, 16-entry / 8 MiB page cache, cooperative yielding.

Business constraints:

- Conventional commits mandatory.
- Priority-based milestones only; no time estimates.
- FIBEX dictionary support is out of scope for this SPEC; the hex dump is the committed baseline for non-verbose payloads.
